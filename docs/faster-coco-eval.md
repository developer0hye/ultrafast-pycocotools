# Comparison with faster-coco-eval

This adds **faster-coco-eval 1.8.0** to the same COCO and Objects365 workloads
used in the public benchmarks. The published Ultralytics validation code uses
`COCOeval_faster`, so it is a relevant additional baseline; this experiment
measures the evaluator, not an end-to-end Ultralytics validation run.

| Workload | pycocotools | faster-coco-eval | ultrafast | Ultrafast speedup vs faster-coco-eval |
|---|---:|---:|---:|---:|
| COCO val2017 / public YOLO11m | 29.87 s | 4.88 s | 2.61 s | 1.87× |
| Objects365 v2 / synthetic predictions | 520.26 s | 100.51 s | 12.43 s | 8.09× |

| Workload | pycocotools RSS | faster-coco-eval RSS | ultrafast RSS |
|---|---:|---:|---:|
| COCO val2017 / public YOLO11m | 1.28 GiB | 1.34 GiB | 0.70 GiB |
| Objects365 v2 / synthetic predictions | 22.62 GiB | 30.46 GiB | 2.37 GiB |

## Numerical agreement

All implementations receive identical annotation and prediction files, checked
by SHA-256. We compare the complete precision, recall, scores and 12 standard
bbox summary statistics, not just rounded AP.

Ultrafast continues to require **byte-identical** results against pycocotools.
Faster-coco-eval has small floating-point differences, which are reported
separately as changed-element counts, maximum absolute differences and
agreement at **absolute tolerance 1e-12, relative tolerance 0**. Passing this
numerical check is not labeled byte identity. The original strict ultrafast
checks have not been relaxed.

Across all six Objects365 sizes, the largest precision difference for faster-coco-eval is 2.22e-16. Every compared array passes the stated numerical tolerance. Complete per-array details are retained in the raw JSON.

## Configuration and scope

- pycocotools 2.0.11, faster-coco-eval 1.8.0, ultrafast-pycocotools 0.1.0;
  Python 3.12.3, NumPy 2.4.4.
- Same AMD EPYC 9554 host and two-core CPU affinity per workload; OpenMP and
  Rayon thread limits 2, OpenBLAS 1. No GPU work.
- `COCOeval_faster(gt, dt, "bbox")` with its default accelerated mode
  (`separate_eval=False`, `extra_calc=False`, `lvis_style=False`). All image IDs
  are selected and standard COCO evaluation parameters are unchanged.
- One run per implementation and input size. Previously published pycocotools
  and ultrafast measurements are reused; faster-coco-eval is measured afterward
  on the same input files. These are observations on a shared host, not
  interleaved repeated trials or guaranteed speedups.
- Timing includes GT indexing, result loading, matching, accumulation and
  summarization. Input JSON parsing, inference and output serialization are
  excluded from timing. Memory is whole-process peak RSS, including parsed
  input and serialization; input preparation runs separately.
- Objects365 uses reproducible **synthetic** predictions and does not measure a
  trained Objects365 detector's accuracy. COCO uses public YOLO11m predictions.

The [raw public results](../bench/results/public_benchmarks.json) and
[scaling results](../bench/results/scaling.json) include all three implementations,
input and array hashes, exact counts, timing phases and numerical differences.
The [scaling figure](scaling.md) uses linear axes and connects measured points.

## Reproduce

```bash
python -m pip install ".[test,plot]" "faster-coco-eval==1.8.0"
python bench/reproduce.py quick --out bench/out/three-way \
  --include-faster --verify-published quick
```

The quick case needs no downloads, images, weights or GPU. For your own saved
predictions:

```bash
python bench/reproduce.py predictions \
  --gt /path/to/annotations.json --pred /path/to/predictions.json \
  --out bench/out/three-way-predictions --threads 2 --include-faster
```

For the full Objects365 comparison, follow the annotation download instructions
in the [reproduction guide](reproducibility.md), then:

```bash
python bench/reproduce.py objects365 \
  --gt /path/to/zhiyuan_objv2_val.json \
  --out bench/out/three-way-objects365 --threads 2 --cpus 0,1 \
  --include-faster --verify-published objects365
```

To freshly measure every size, use the predictions generated by that command:

```bash
python bench/scale.py \
  --gt /path/to/zhiyuan_objv2_val.json \
  --pred bench/out/three-way-objects365/predictions.json \
  --out bench/out/three-way-scaling --threads 2 --cpus 0,1 --include-faster
python bench/plot_scaling.py \
  --results bench/out/three-way-scaling/scaling.json \
  --out bench/out/three-way-scaling/figure
```

Choose new output directories. Omit CPU affinity outside Linux. Full-size
faster-coco-eval evaluation needs tens of GB of RAM on this workload.
The fresh three-way commands rerun all implementations. To measure only the
additional backend against already saved inputs, use
`bench/compare_saved_predictions.py --backend faster-coco-eval --gt ... --pred ... --out ...`;
`compare_numerically()` in `bench/reproduce.py` compares its arrays with an
existing reference output directory.
